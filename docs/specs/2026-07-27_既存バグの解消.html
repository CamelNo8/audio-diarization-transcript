1. 背景・目的

リファクタリング作業（Phase 0〜3）の過程で既存バグを 2 件報告したが、「Refactor 段階では振る舞いを変えない」（規約2.1） という取り決めのため未修正のまま残している。クライアントの判断により、 Phase 4（Web アプリ層の分割）に着手する前に既存バグを解消することになった。

あわせて、次に分割する app.py を含むコードベース全体を対象にバグ探索を行い、 確定したものを本書で修正する。先にバグを潰しておくことで、Phase 4 の分割中に 「元からのバグ」と「分割で入れ込んだバグ」が混ざるのを防ぐのが目的である。

B-1 重大 — 出力ファイル名のパストラバーサル（規約7.1 違反）

現象

Web の 3 つの処理ルートは、フォームで受け取った出力ファイル名を検証せずに TEMP_DIR と結合している。 

app.py:367  output_srt_path = TEMP_DIR / output_srt_name      # /process/transcription
app.py:368  output_csv_path = TEMP_DIR / f"{srt_stem}.csv"    # 同上（stem 経由）
app.py:495  output_path     = TEMP_DIR / output_csv_name      # /process/matching
app.py:555  output_path     = TEMP_DIR / output_srt_name      # /process/generation

pathlib の / 演算子は、右辺が絶対パスなら左辺を捨てる。 また ../ も素通りする。_job_dir() は job_id を厳格に検査しているのに、 出力ファイル名だけが無検査で残っている。

実際に確認した動作

POST /process/generation  output_srt_name="../../TRAVERSAL_TEST.srt"
  → HTTP 200
  → /Users/hiyori/dev/TRAVERSAL_TEST.srt が生成された（temp/ の外）

TEMP_DIR / "/tmp/abs.srt"  → /tmp/abs.srt           （絶対パスで左辺が消える）
TEMP_DIR / ""              → .../temp（ディレクトリ自身）
影響の範囲について（過大評価しないための注記）
本アプリは 127.0.0.1:8000 でローカル起動する個人用ツールであり、外部公開されていない。 そのため「第三者による攻撃」というより「打ち間違いでリポジトリ外にファイルを撒く」事故が実害の中心になる。 ただし規約7.1 が要求する入力検証が欠けているのは事実であり、Phase 4 でルートを分割する前に直しておく。

修正方針

  • src/common/ に出力ファイル名の検証関数を新設する（例: safe_output_name(raw, default)）。
    • Path(raw).name を取り、元の文字列と一致しなければ不正とする（../・絶対パス・区切り文字を弾く）
    • 空文字・.・.. は既定名にフォールバックする
    • 既存の vdb.sanitize_name（DB名・話者名用）とは用途が違うため別関数にする。 ファイル名は拡張子を含むため . を許可する必要がある
  • 3 ルートすべてに適用する。output_csv_path は検証後の名前の stem から作る
  • ダウンロード URL は検証後の名前で組み立てる（現状は不正名だとリンクが 404 になる）

ふるまいの変化

不正な出力名を指定した場合、これまで temp/ の外に書かれていたものが temp/ 内に書かれる。 正常な名前（既定値の transcription.srt・対応表.csv・subtitles.srt、 および日本語を含む通常のファイル名）に対する挙動は一切変わらない。

あわせて入れる多層防御（バグではない）

GET /download/{filename} にも Path(filename).name の検査を入れる。 調査では /download/../app.py・%2F エンコード版のいずれも FastAPI のルーティングに 弾かれて 404 になり、現時点で到達できないことを確認済みのため、これはバグの修正ではなく予防措置である。

B-2 中 — distil モデル指定が large-v3 に化ける（Phase 3 で報告済み）

現象

FASTER_WHISPER_SIZES は前方一致ではなく部分一致（if size in lowered）で走査する。 "distil-large-v3" は "large-v3" を含むうえ、リスト上で "large-v3" のほうが先にあるため、 distil 指定は決して選ばれない。 

to_faster_whisper_model("distil-large-v3") → "large-v3"                  （期待: "distil-large-v3"）
to_hf_whisper_repo("distil-large-v3")      → "openai/whisper-large-v3"   （期待: "distil-whisper/distil-large-v3"）
to_faster_whisper_model("distil-large-v2") → "large-v2"                  （期待: "distil-large-v2"）

_HF_WHISPER_REPO には distil 用のエントリが用意されているのに、 そこへ到達する経路が無い（＝デッドな対応表になっている）。

踏める経路

Web UI「Whisper モデル品質」→「カスタム（モデルIDを直接入力）」の自由入力欄 （templates/index.html:235）、および CLI の --mlx_model。 利用者は distil（軽量・高速）を選んだつもりで、実際には large-v3 の重い推論が走る。 distil-whisper/distil-large-v3 とフルリポジトリ名で書いた場合だけは素通しされるため、実害は限定的。

修正方針

  • FASTER_WHISPER_SIZES の順序を、他の候補を部分文字列として含む名前ほど先になるよう並べ替える。 distil-large-v3 / distil-large-v2 を large-v3 系より前に置く
  • 「長い名前から先にマッチさせる」というコメントは既にあるが実態が伴っていないため、 並び順が仕様であることをテストで固定する（順序を壊したら落ちるテストを書く）
  • mlx 経路は _MLX_REPO に distil のエントリが無い。クライアント決定に従い、 「mlx-whisper は distil モデル非対応のため large-v3 を使用します」と警告ログを出してから 既定へフォールバックする（黙って差し替えない）

更新する既存テスト

tests/test_transcription_backend.py の test_distil指定はlarge_v3として解決される既存挙動 は現状（バグ）を固定しているテストなので、 正しい期待値へ書き換える（テスト名も実態に合わせて改名する）。

B-3 中 — 発話 0 件のとき「保存しました」と嘘の完了報告をする

現象

process_and_save_to_csv() は Whisper がセグメントを 1 件も返さなかったとき、 CSV を書かずに True（成功）を返す。 

src/diarization/processor.py:172-174
    if not segments:
        logger.warning("No speech segments detected by Whisper.")
        return True          # ← CSV を書かないまま成功扱い

実際に確認した動作

戻り値 = True / CSV 存在 = False
→ CLI (src/cli/runner.py:216) は
   "Processing complete. Results saved to " と表示して終了コード 0 を返す
→ しかし  は存在しない

Web 側（app.py:415）は output_csv_path.exists() も見ているため誤動作はしないが、 「文字起こし処理に失敗しました」という原因とずれたメッセージが出る（実際は無音・無発話）。

修正方針

  • セグメントが 0 件でもヘッダ行だけの CSV を書き出す。 「処理が完走したら CSV が存在する」という後段（CLI・Web）の前提を満たす
  • 警告ログ（No speech segments detected by Whisper.）はそのまま残す
これは振る舞いの変更です（要承認）
「発話 0 件」を 失敗 と 中身のない成功 のどちらとして扱うかは設計判断のため、方針を明記しておく。
本書では後者（ヘッダのみの CSV を出して成功）を採る。理由は (1) 無音・BGM のみの音声を投入したときにエラーにするのは過剰、 (2) 戻り値 True という現在の意味を変えずに矛盾だけを解消できる、 (3) Web 側は 0 行の SRT とクラスタ 0 件のジョブが作られ、画面の流れが途切れない、の 3 点。
「失敗（False を返す）にすべき」というご判断であれば、そちらへ変更する。

B-5 小 — CPU フォールバック時にモデルキャッシュが効かない

現象

src/transcription/faster_whisper.py:67-68
    model, cache_key = _load_model(model_name, device, compute_type)
    _MODEL_CACHE[cache_key] = model      # ← 実際に使えた設定のキーだけ登録される

CTranslate2 が CUDA 非対応ビルドの環境（aarch64 = Spark など）では、 _load_model が (model_name, "cpu", "int8") というキーを返す。 一方 _get_model の探索キーは (model_name, "cuda", "float16") のままなので、 次の呼び出しでもキャッシュがヒットせず、毎回 CUDA 初期化を試みては失敗して CPU に落ちる。 モデル読み込みは重い処理のため、実行のたびに無駄なコストがかかる。

修正方針

  • フォールバックが起きた場合、要求時のキーにも同じモデルインスタンスを登録する （実際に使った設定のキーと両方を張る）
  • 2 回目以降の _get_model が読み込みを呼ばないことをテストで確認する（WhisperModel はモック）

出力される文字起こし結果は変わらない。変わるのは 2 回目以降の所要時間だけ。

B-6 小 — 環境変数を元の値へ戻していない

現象

src/diarization/registry.py:70-78
    except Exception:
        os.environ["HF_HUB_OFFLINE"] = "0"
        try:
            return SpeakerIdentifier(...)
        finally:
            os.environ["HF_HUB_OFFLINE"] = "1"   # ← 元の値ではなく決め打ちで "1"

エントリポイント（main.py / app.py）が "1" を設定しているため通常は一致するが、 利用者が HF_HUB_OFFLINE=0 を明示して起動した場合、この関数を一度通っただけで 意図せずオフラインモードに切り替わる。「一時的に外して戻す」という関数の意図と実装がずれている。

修正方針

  • 呼び出し前の値を保存し、finally で元の値へ戻す（未設定だった場合はキーごと削除する）

B-7 小 — スキップしていないのに「スキップします」と警告する

現象

src/subtitle/exporter.py:60-73  _is_usable_row()
    if all(row[col] for col in REQUIRED_COLUMNS):
        return True
    logger.warning("警告: N行目に空のデータがあります。スキップします。 (speakerは空でも可)")
    if not all(row[col] for col in _ESSENTIAL_COLUMNS):
        logger.warning("警告: N行目に必須データ...がありません。スキップします。")
        return False
    return True          # ← 話者名だけ空の行は採用されるのに、警告だけ出ている

話者名（speaker）は空でよい仕様なのに、空だと必ず「スキップします」と警告が出る。 実際にはスキップされず字幕になるため、ログが実際の動作と食い違う。 対応表 CSV では話者名の空欄はごく普通に発生するため、警告が大量に出て本当の警告が埋もれる。

修正方針

  • 必須列（start_time / end_time / subtitle_text）の判定を先に行い、 欠けている場合だけ「スキップします」と警告する
  • 話者名のみが空の行は警告を出さずに採用する（仕様どおりの正常系のため）

字幕の出力内容は変わらない。変わるのはログだけ。

5. 処理フロー（作業手順）

バグ 1 件ごとに Red-Green を回す（規約2.1）。修正は1 バグ 1 コミットとし、あとから個別に追える形にする。

B-1 (重大) → B-2 (報告済み) → B-3 → B-4 → B-5 → B-6 → B-7
  各バグについて:
    ① バグを再現する失敗テストを書く（Red を確認して提示）
    ② 修正する（Green を確認）
    ③ 全テストが緑であることを確認（回帰が無いこと）
    ④ 仕様書の ToDo を更新してコミット
最後に:
    ⑤ pytest 全緑 + ruff + アプリ起動 + CLI --help のまとめ確認
    ⑥ 報告・承認 → アーカイブ → Phase 4 へ

6. エラー処理方針

  • 不正な入力は例外にせず、安全な既定値へフォールバックする（B-1）。 個人用ツールであり、打ち間違いで処理全体が止まるより、既定名で処理が通るほうが使いやすいため。 フォールバックしたことは警告ログに残す
  • 既存の例外の捕捉位置は変えない。 握りつぶしを新たに追加しない
  • 環境変数の一時変更は必ず try/finally で元へ戻す（B-6）
  • ログの文言は、実際に起きたことと一致させる（B-3・B-7）。 「スキップします」と書いたらスキップする、「保存しました」と書いたら保存されている状態にする
