2. 実装前に判明した追加の問題

Step 1 の実行中、Web アプリ全体が応答しなくなっている（#3 の実害）。
process_transcription は async def でありながら、中で AudioProcessor（ブロッキング処理）を直接呼んでいる。asyncio のイベントループが その間ずっと占有されるため、文字起こし中は / も声紋DB画面も開けない。 接続タイムアウトより先に、こちらのほうが体感される問題である。 非同期ジョブ化ではワーカースレッドへ処理を逃がすので、これも同時に解消する。

3. 設計

3-1. #3 文字起こしの非同期ジョブ化

Spark サーバー（src/spark/server.py）と同じ「job_id を即返して裏で処理」方式に揃える。

POST /process/transcription
      ├─ 入力検証（ffmpeg / HFトークン / 音声 / 声紋DB）はここで同期に行う
      │  → 不正なら今までどおり partials/error.html を返す
      ├─ job_id を発行し、status="queued" で job.json を書く
      ├─ ワーカースレッドを起動して処理を任せる
      └─ partials/transcription_progress.html を返す（htmx のポーリング付き）

GET  /process/transcription/{job_id}/status   ← htmx が2秒ごとに叩く
      ├─ running  → transcription_progress.html（ポーリング継続）
      ├─ done     → success_transcription.html（ポーリング属性なし → 自然に停止）
      └─ error    → error.html（同上）
項目方針
ポーリングの止め方 htmx の自己置換（hx-swap="outerHTML"）を使う。完了時に返す断片には hx-trigger を含めないため、追加の JavaScript なしでポーリングが止まる。
ワーカーの起こし方 threading.Thread(daemon=True)。AudioProcessor は CPU/GPU 依存の ブロッキング処理なので、BackgroundTasks（同一タスク内で走る）ではなくスレッドに逃がす。 Spark サーバーと同じ形にする。
進捗ログ 現行の capture_root_logs() はルートロガーにハンドラを足す。 スレッド化すると他ジョブのログが混ざるため、 ワーカースレッドの thread ident で絞る logging.Filter を足す。 捕捉したログは job.json に書き、進捗画面に末尾を出す。
同時実行 本作業では直列化しない。 現状も同時に複数投げれば重い処理が並走する点は同じで、 キューを入れると設計判断（同時実行数・待ち表示）が増えるため。 スレッド分離により、少なくとも並走中も画面は応答するようになる。
プロセス終了時 daemon スレッドなのでサーバー停止で打ち切られる。status は "running" のまま残る。再起動後にその表示になったら、やり直していただく想定 （README に明記する）。

3-2. #2 ジョブ状態のディスク永続化

Web（src/web/jobs.py）

  • メモリキャッシュ _JOBS を廃止し、job.json を唯一の真実にする。 読むたびにファイルから読む。ジョブ1件は数KBで、1リクエストに1回程度なので実測上の問題はない。
  • 書き込みをアトミックにする。ワーカースレッドが書いている最中に ポーリングのリクエストが読むため、現行の「開いて上書き」だと壊れた JSON を読みうる。 一時ファイルに書いて os.replace() で差し替える。
  • 部分更新用に update_job(job_id, **fields) を足す（status とログの更新に使う）。

Spark（src/spark/server.py）

  • JOBS 辞書を廃止し、WORK_DIR/<job_id>.json に読み書きする。 再起動してもジョブの結果が消えない。
  • Web と同じアトミック書き込みを使う。src/common/ に共通の JSON 読み書きを置き、Web / Spark の両方から使う（規約4.3）。
  • _JOBS_LOCK は引き続きスレッド間の直列化に使う。

3-3. #5 声紋DB・話者の削除をゴミ箱へ

voice_databases/
├── テストDB/            ← 通常のDB
└── .trash/              ← 退避先（新設）
    ├── 20260728-143000_テストDB/        ← DB ごと削除した場合
    └── 20260728-143512_テストDB_太郎.wav ← 話者1件を削除した場合
項目方針
退避方法shutil.rmtree / unlink をやめ、 shutil.move で .trash/ 配下へ移す。名前は <YYYYMMDD-HHMMSS>_<元の名前>。同秒に同名を消した場合は連番を付ける。
一覧からの除外list_databases() は ドットで始まる名前を読み飛ばす。これをしないと .trash が DB として画面に出てしまう。
名前の検証sanitize_name() が ドットで始まる名前を弾くようにする。.trash を DB として 作成・参照・削除できてしまう経路を塞ぐため（規約7.1）。 既存の「. / .. を弾く」検査を一般化する形になる。
GUI の復元機能作らない。 ディレクトリを手で戻すだけで復旧できるため。 README に場所と戻し方を書く。
自動削除しない。 溜まったら手で消す運用にする （音声データの保存期間を本作業で変えないため。規約7.4）。
振る舞いの変化（意図的）: 削除後もディスク使用量が減らなくなる。声紋 WAV は1件あたり小さいが、 DB を作り直しては消す使い方をすると .trash/ が育つ。 README に「不要になったら voice_databases/.trash/ を手で空にしてください」と明記する。

6. セキュリティ考慮

項目方針
7.1 入力検証job_id のパストラバーサル検査（job_dir()）は現行のまま維持する。 新しい /status ルートも同じ検査を通す。DB名の検証はドット始まりを弾く方向に強める。
7.2 秘匿情報HF トークンは job.json に書かない（現行も書いていない）。 ワーカースレッドへは引数で渡す。進捗ログに新たにトークンやパスが出ないことを確認する。
7.4 データ保護保存先は現行どおり temp/ と voice_databases/ に限定する。 .trash/ は voice_databases/ の中に置くため、.gitignore の対象に既に含まれる。 保存期間だけは延びる（削除しても残るため）。上記のとおり README に明記する。
7.5 Web進捗断片も Jinja2 の自動エスケープに任せる。| safe は追加しない。
7.6 依存追加なし。 標準ライブラリ（threading / os.replace）と htmx の既存機能だけで実現する。
