5. 処理フロー（作業手順）

フェーズ単位で 「特性テストを書く → 緑を確認 → 移動・分割 → 再度緑を確認 → 報告・承認」 を回す。 各フェーズは独立したコミットにする（規約11.1）。

Phase 0  基盤整備（pytest / ruff / src 骨組み / 純ロジックの特性テスト）
   ↓
Phase 1  common/ + config.py の確立（重複の共通化・print→logger）
   ↓
Phase 2  字幕マッチング（subtitle_matcher / subtitle_exporter）の分割
   ↓
Phase 3  音声処理コア（audio_processor / speaker_identification / transcription_backend）の分割
   ↓
Phase 4  Web アプリ層（app.py）の分割
   ↓
Phase 5  Spark 連携・エントリポイント・README・リンタ全体適用・最終確認

各フェーズの終了時に (a) pytest 全緑の出力、(b) 変更ファイル一覧、 (c) 規約4.1 の残違反箇所 を提示して承認を得る。承認前に次フェーズへ進まない。

6. エラー処理方針

  • 本作業では例外の扱いを変更しない。 既存の except Exception や握りつぶしを見つけても、 振る舞いが変わるため直さない（規約2.1 Refactor 段階では振る舞いを変えない）。該当箇所は一覧にして報告し、別タスクとして提案する。
  • 例外は移動先モジュールでもそのまま送出させる。捕捉位置を変えない。
  • print → ロガー置換は、出力文言と出力タイミングを維持する（規約2.7「ログ出力の文言変更など振る舞いに影響しない変更」に準じる）。 ログレベルは既存の意味に合わせて割り当てる（エラー表示は ERROR、進捗は INFO）。
  • 移動にともなう import 失敗・パス解決の失敗は、フェーズ内のスモークテスト（アプリ起動・CLI --help）で検出する。
