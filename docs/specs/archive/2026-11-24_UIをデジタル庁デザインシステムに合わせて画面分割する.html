UIをデジタル庁デザインシステムに合わせて画面分割する

作成日: 2026-11-24 ／ 状態: 完了（2026-11-24 実装・確認ずみ） ／ 対象: Web UI（templates/, src/web/）

1. 目的と背景

今の Web UI は、トップページ（/）に Step 1（文字起こし＆話者分離）・Step 2（マッチング）・Step 3（字幕生成）の 3つのカードを横並びで置いている。1画面に全部あるため、次の問題がある。

  • 画面の幅を3分割しているので、1つの手順に使える領域が狭い（Step 1 は設定項目が多く、縦に長い）。
  • 今どの手順にいるのかが分かりにくい。まだ実行できない Step 2 のボタンも常に見えている。
  • 見た目は Tailwind の既定色（紫・青・緑のグラデーション）で、配色・文字サイズ・フォーカス表示に根拠がない。

そこで デジタル庁デザインシステム（DADS β版）に合わせて見た目を作り直し、Step 1〜3 をそれぞれ別の画面にする。 手順が1画面1つになるので、画面の上に「今は 2 / 3 番目」と出せるようになり、入力欄も広く取れる。

2. 決定事項（確認済み）

項目決定理由
トップ画面 / をそのまま Step 1 にする 概要ページを挟まない。クリック数が最小。手順の移動は画面上部のステップ表示で行う。
CSS の持ち方 自前の CSS 1枚（static/css/dads.css）。Tailwind CDN は外す DADS の数値をそのまま書ける。大学プロキシや Spark 上でも外部CDNに依存せず崩れない。
対象画面 Step 1〜3 ＋ 声紋DB管理（/databases）＋ ラベル付け（/unknowns）の全画面 一部だけ新デザインだと見た目が混ざるため。ただし下記フェーズに分けて進める。
Step 1 完了後 完了画面に「Step 2 へ進む」ボタンを出す（自動遷移しない） SRT のダウンロードと未登録話者のラベル付けを、先へ進む前に確認できるようにする。

3. 画面構成と URL 設計

処理を実行する POST の口（/process/*）は今のまま変えない。画面を表示する GET を追加するだけにする。

URLメソッド内容変更
/GETStep 1: 文字起こし＆話者分離中身を Step 1 だけに
/matchingGETStep 2: マッチング（対応表作成）。?job_id= で Step 1 の結果を引き継ぐ新規
/generationGETStep 3: 字幕生成。?csv= で Step 2 の出力名を案内に出す新規
/process/transcriptionPOST文字起こしの受付（非同期ジョブ）なし
/process/transcription/{job_id}/statusGET進捗パネル（htmx が2秒ごとに取得）なし
/process/matchingPOSTマッチング実行なし
/process/generationPOST字幕生成なし
/databases, /api/databases/*GET/POST/DELETE声紋DB管理見た目のみ
/unknowns/{job_id}GET/POST未登録話者のラベル付け見た目のみ
/download/{filename}GET生成物のダウンロードなし
/static/*GETCSS などの静的ファイル新規

手順の間のデータの受け渡し

今は「1画面に全部ある」ことを利用して、Step 1 の完了時に JavaScript で Step 2 の隠しフィールド （#step2-job-id）へ job_id を書き込んでいる。画面を分けるとこれは使えないので、URL のクエリパラメータで渡す。 

Step 1 実行 → 完了パネルに「Step 2 へ進む」
                  ↓ /matching?job_id=20261124-153012-ab12
Step 2 画面      job_id を隠しフィールドに入れ、Step 1 の SRT 名を画面に表示
                 （job_id が無ければ「Step 1 を先に実行してください」と案内し、実行ボタンは押せない）
Step 2 実行 → 完了パネルに「Step 3 へ進む」
                  ↓ /generation?csv=対応表.csv
Step 3 画面      「対応表.csv をダウンロードして編集し、ここにアップロード」と案内を出す

Step 3 はファイルのアップロードのまま

対応表CSVは「人が中身を直してから字幕にする」のが前提なので、Step 2 の出力を自動で渡すことはしない。 Step 3 の画面には、Step 2 で作ったファイル名を案内として出すだけにする。

4. 使うデザインの値（DADS）

DADS の配布物は Figma のデザインデータ（CC BY 4.0）が原典で、サイトの色のページも「実際の色データは Figma を参照」と書いている。 下の数値は 公式の HTML 実装例リポジトリ（digital-go-jp/design-system-example-components-html、MIT ライセンス）の CSS から取った実測値で、 これを自前の CSS に書き写して使う。公式の CSS ファイルそのものをコピーはしない（著作権表示の管理が増えるため）。

フォーカス表示は変えない

DADS は「フォーカスインジケーターは黄色と黒の二重構造で、いかなる場合も変更してはいけない」と明記している。 今の Tailwind の focus:ring-2 focus:ring-purple-400 は全部これに置き換える。

文字と間隔

  • フォント: "Noto Sans JP", sans-serif（等幅は "Noto Sans Mono"）。ウェイトは 400 と 700 の2つだけ。
  • 本文: 16px / 行間 1.7 / 字間 0.02em。14px 未満は使わない（今の UI は text-xs(12px) を多用しているので、全部 14px 以上に直す）。
  • 見出し: 32px/1.5、24px/1.5、20px/1.5、18px/1.6（いずれも bold、字間 0.01〜0.02em）。
  • 間隔: 8px を基準にし、8 / 16 / 24 / 32 / 40 / 64px を使う。
  • ブレークポイント: 768px（これ未満をモバイル扱い）。1カラムに落とす。
  • コンテンツの最大幅は DADS に規定が無いため、本文が読める幅として 840px（Step の画面）/ 1200px（DB管理の一覧）を自分で決める。

ヘッダー・パンくず・ステップナビゲーションは、公式の HTML 実装例が「提供予定」で CSS が無い。 ページの画像の説明（完了は灰色の丸＋チェック、現在は黒塗りの二重丸、未完了は白い丸）に合わせて自分で作る。

すでにある部品を使い回すところ

  • jobs.load_job() … Step 2 の画面で job_id から Step 1 の SRT 名（srt_filename）を取り出す。新しい関数は作らない。
  • matching.py の _resolve_step1_srt() … 実行時の解決は今のまま。画面表示では使わない（存在しない job_id でも画面は出す）。
  • templating.templates / render_error() … そのまま使う。render_error が返す断片の見た目だけ変える。
  • is_safe_output_name() … 出力ファイル名の検証。変更しない。

7. テストの方針

見た目（CSS・HTML の体裁）は自動テストの対象にしない。代わりに画面が出ること・手順の引き継ぎが効くことをテストする。 テストは tests/test_web_routes.py に足す（既存の client フィクスチャを使う）。

種別テスト
正常系GET / に Step 1 の見出しが含まれる／GET /matching・GET /generation が 200 を返す
正常系GET /matching?job_id=<完了済みジョブ> に Step 1 の SRT ファイル名が含まれる
境界値GET /matching（job_id なし）で「Step 1 を先に実行」の案内が出て、実行ボタンが disabled になっている
異常系GET /matching?job_id=存在しないID でも 500 にならず、案内付きで画面が出る
異常系GET /matching?job_id=../../etc/passwd で例外にならない（jobs.load_job が ValueError を投げるので、画面側で受け止める）
正常系GET /static/css/dads.css が 200 を返す

8. 今回やらないこと

  • 処理の中身（文字起こし・話者照合・マッチング・字幕生成）のロジックは一切変えない。
  • Step 2 の出力を Step 3 へ自動で渡す機能は作らない（対応表は人が編集する前提のため）。
  • DADS の公式 CSS / npm パッケージ / Tailwind テーマプラグインの取り込みはしない（自前 CSS 1枚にする決定のため）。
  • ダークモード、多言語対応、ログイン機能は作らない。
  • 先のセキュリティ確認で挙げた3点（torch.load のパッチ範囲、Spark API の 0.0.0.0 の例、spark-up.sh のIP直書き）はこの作業に含めない。別の作業として扱う。
