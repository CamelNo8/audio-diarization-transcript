1. 前提として確認した事実

正解字幕（~/Desktop/字幕（ココナラで依頼したもの） の9本）を解析して、次を確認した。

項目実測設計への影響
話者表記 本文先頭の （話者名）。1エントリに複数個入ることがある。効果音・音楽は [荘厳な音楽] のように []、または （軽快なBGM）。 抽出するのは （） だけ（[] は常に非発話なので最初から見ない）。（） の中の効果音・音楽ラベルはキーワードで除外する。
時間の重なり 9本すべてで重複区間ゼロ（次エントリの in 点が前エントリの out 点以降）。 正解字幕から「重なり時間の割合」を測ることはできない。自動化①は複数話者エントリ率で代替し、自動化②では pyannote の出力から時間ベースで測る。

クリップ長 納品字幕は 610〜923 秒（≒10〜15分）。5分クリップ2本を切り出す余地はある。 窓長 300 秒。ただし2窓が重ならないことを保証する。
「重なり率」は予稿でも「おおよその割合」と書かれている。 自動化①の定義（複数話者ラベルを含むエントリ率）はその「おおよその割合」の運用的な定義として妥当だが、 ミュトスのように納品者が重なりを字幕に落とさなかった番組では 0 になる。 この限界は仕様として明記し、レポートにも根拠件数（overlap_entry_count）を併記する。 0 になった番組では、実質「話者交替回数」だけで難易度が決まることを標準出力で警告する。
初版の数値（コンビニ店長 130/219件など）は誤りだったので訂正した。 納品字幕は複数行のエントリでは各行に同じ話者名を前置する （（佐藤）ありがたいことに / （佐藤）5回目になりました）。 ラベルの個数で数えると、この繰り返しを重なりとして数えてしまう。 重なりは「別人が2人以上いるエントリ」で数えるのが正しく、そうすると割合は 0.0〜11.5% になる。 実装ではこれを tests/test_srt_stats.py の test_同じ話者が各行に繰り返されても話者は1人と数える で固定した。

1-1. 重なり率は2種類あり、混ぜてはいけない

クライアント指摘のとおり、時間ベースの重なりは pyannote の出力から取れる。ただし正解字幕由来のものとは別物なので、変数名を分ける。

変数出どころ定義使う場所
overlap_entry_ratio 正解字幕 人物ラベルを2つ以上含むエントリ ÷ 発話エントリ数。 自動化①のクリップ選定（正解字幕しか無い段階で使える唯一の指標）。
overlap_time_ratio pyannote（Annotation） 2人以上のクラスタが同時に喋っている時間 ÷ 発話総時間。pyannote/speaker-diarization-3.1 は powerset 型のセグメンテーションで重なりを出力できるため、Annotation には同時刻に複数ラベルが立つ区間が含まれる。 自動化②の説明変数。
pyannote から取るには、いまのアプリに出力を1つ足す必要がある。 現状 src/diarization/processor.py は Annotation をメモリ上で使うだけでディスクに残していない （残るのは話者名を付けた transcription.csv だけで、そこには重なりの情報が消えている）。 そこで process_and_save_to_csv に RTTM の書き出しを追加する（出力CSVと同じ場所に <CSV名>.rttm）。 Web UI と CLI は両方この関数を通るので変更は1箇所で済む。

この方式にする理由は、評価ツール側で pyannote を再実行しないため。再実行すると denoise の有無や話者数ヒントで結果が変わり、 「実際に評価した実行とは違う分離結果の重なり率」を報告してしまう。実行時に残せば、その実行が実際に見た重なりを報告できる。
解釈上の注意（分析時に一言添えるべき点）。 overlap_time_ratio はシステムの出力なので、説明変数として使うと循環しうる。 重なりを検出し損ねた区間ほど重なり率が低く出るため、「重なり率が低いから容易だった」という説明が 「重なりを見落としたから低く見えた」と区別できない。 そのため自動化②のレポートには両方（overlap_entry_ratio・overlap_time_ratio）を並べて出す。 正解字幕由来の値と大きく食い違うクリップは、重なりの見落としが起きた候補として目視確認できる。

3. 共通土台：srt_stats.py

3-1. パース

既存の src/subtitle/loader.py は「音声認識SRT（[話者]前置）」専用で、BOM や複数話者に対応していないため流用せず、この用途のパーサを持つ。 時刻は HH:MM:SS,mmm / .mmm の両方を受ける。BOM (utf-8-sig) を除去する。

3-2. 話者ラベルの抽出と非発話判定

クライアント指示により、抽出対象は （…）（半角 (…) も同様）だけとする。 […] ［…］ は効果音・音楽の表記なのでラベル候補として拾わない。

  • （） の中に入っている効果音・音楽（（軽快なBGM） （笑い） （ドアの作動音） など）はキーワードで除外する。 既定の語（部分一致）は BGM 音楽 効果音 ジングル 笑い 拍手 ざわめき 歓声 と、末尾が 〜音 のもの。 加えて 笑 は完全一致のときだけ非発話とする（部分一致にすると 笑福亭 のような人名を巻き込むため）。 --non-speech で語を追加できる。
  • ラベルとみなすのは行頭・空白の直後・直前のラベルの直後から始まる （） だけ。 これにより （岸谷）あとはClaude（クロード） の「クロード」を話者と誤認せず、 （吉村）あ、そうなんだ （松尾）そうですね のような1行に2話者が並ぶ表記（重なりの手がかり）は拾える。
  • ラベルの後ろに付く注記（（マクロン大統領（VTR）） （中嶋／手話・音声通訳））は --strip-suffix が指定されたときだけ ／ ・ 以降と入れ子の括弧を落として同一話者に寄せる。既定は落とさない（別名として扱う）。
キーワード判定は完全ではない。 「（謎の声）」は登録話者だが「（驚く声）」は非発話、のように語では割り切れない例がある （そのため既定の語に 〜声 は入れない。「〜声」は話者名として残る）。 そこで非発話と判定したラベルの一覧と、話者と判定したラベルの一覧を必ず標準出力に出す。 1本あたり十数語なので目視確認は数秒で済み、誤りは --non-speech / --speaker で上書きできる。

3-3. 説明変数（予稿 4.3）

変数名定義
duration_sec区間長（秒）。
speaker_count区間に登場する話者ラベルの種類数（非発話を除いたもの）。自動化①ではこれを「登録話者数」の代理として使う（実験条件 4.2 で主要登場人物は全員登録する前提なので、字幕に出てくる名前付き話者数がほぼ登録話者数になる）。
utterance_count発話を含む字幕エントリ数（非発話のみのエントリは数えない）＝発話総数。
speaker_change_count発話エントリを時系列に並べ、代表話者（そのエントリの最初の話者ラベル）が直前と変わった回数。
speaker_change_per_minspeaker_change_count / (duration_sec/60)。区間長が違っても比較できるようにする。
overlap_entry_count / overlap_entry_ratio話者ラベルを2つ以上含むエントリ数と、その発話エントリに対する割合。
speech_time_ratio発話エントリの合計時間 ÷ 区間長。無音・音楽が多い区間を見分ける補助。
overlap_time_ratio自動化②のみ。 RTTM から算出する、2人以上が同時に喋っている時間の割合（3-4 節）。

3-4. RTTM からの重なり時間（自動化②用）

src/diarization/processor.py が書き出した RTTM を読み、クラスタごとの区間を秒単位の数直線に重ねて 同時刻に2つ以上のクラスタが立っている時間の合計を求める。区間の端点でイベントを作って走査する（区間数は数百なので単純な走査で足りる）。

overlap_time_ratio = 2人以上が同時に喋っている時間 / 1人以上が喋っている時間

RTTM が無い場合は overlap_time_ratio を空欄にして他の指標だけ出す（評価が止まらないようにする）。

「Unknown_NN となった要因」は音を聴かないと決まらないので自動化の対象外。レポートに空欄の記入列として出すだけにする。

4. 自動化①：clip_selector.py

4-1. 手順

入力は正解字幕 SRT だけ（クライアント指示）。声紋データベースは参照しない。 登録話者数の代わりに、字幕に出てくる話者ラベルの種類数（speaker_count）を使う。
  1. 正解 SRT を読む。
  2. 候補窓の列挙。 各発話エントリの in 点を窓の開始候補とし、そこから --length（既定 300 秒）以上になる最初の発話境界（=あるエントリの out 点）を窓の終わりにする。 これで切り出しは必ず発話境界になり、発話を途中でぶつ切りにしない。 実長が --length ± --tolerance（既定 ±15 秒）に収まらない候補は捨てる。
  3. 難易度スコア。 全候補窓の speaker_change_per_min と overlap_entry_ratio をそれぞれ z 正規化して単純に足す（重みは --weight-change / --weight-overlap で変更可、既定 1:1）。 標準偏差が 0 の指標は寄与 0 とする（＝ミュトスのように重なり表記が無い番組では、話者交替だけでスコアが決まる。この場合は警告を出す）。
  4. 話者数の揃え。 --target-speakers N が指定されたら |speaker_count - N| × --speaker-penalty（既定 0.5）を難易度スコアから引く。 これで「可能な範囲で揃える」を効かせる。未指定なら無効。
  5. 2窓の選択。 時間が重ならない2窓の全組み合わせを総当りし、 score(hard) - score(calm) が最大になるペアを採る（候補は数百なので総当りで足りる。 「スコア最大の窓を先に固定して残りから探す」貪欲法より良いペアが選べる）。 スコアの高い方を「hard（重なり・話者交替が多い）」、低い方を「calm（落ち着いた）」とする。 重ならない2窓が作れない場合（＝動画が10分未満など）はエラーメッセージを出して終了する。

4-2. 出力

  • 標準出力に人が読める要約（各窓の in/out、説明変数、話者一覧、非発話と判定したラベル一覧）。
  • --out-csv で説明変数を1行1クリップの CSV に。複数番組を --append で1枚に集約できる。
  • --out-srt-dir で各窓に対応する正解 SRT をクリップ先頭を 0 秒に振り直して切り出し保存（そのまま評価の正解データになる）。
  • 切り出し用 ffmpeg コマンドを表示（実行はしない。-ss/-to は既存 src/common/audio.py と同じ書式に揃える）。
uv run python -m src.evaluation.clip_selector \
    --srt "字幕（ココナラで依頼したもの）/転スラ.srt" \
    --video 転スラ1話.mp4 \
    --target-speakers 5 \
    --out-csv docs/experiment/clip_variables.csv --append \
    --out-srt-dir docs/experiment/gt

5. 自動化②：evaluator.py

5-1. 対応付け（クライアント選択：本文テキストで対応付け）

正解 SRT とアプリ生成 SRT は同じ人手文字起こし文が元なので、本文が一致するはず。ただしアプリ側は話者名を （話者名）として本文に前置し、しかも話者が変わったときだけ前置する（src/subtitle/exporter.py の仕様）。 そこで両者から話者ラベルを剥がし、src/subtitle/ngram.normalize_text で正規化してから difflib.SequenceMatcher で順序を保った 1:1 対応を取る。 完全一致で対応しなかった行は、前後の未対応行の中から類似度が --min-similarity（既定 0.6）以上で最大のものに割り当てる。 それでも余った行は「対応なし」として件数だけ報告する（in 点・話者の評価対象からは外す）。

アプリ側の話者ラベルは「変わったときだけ前置」なので、剥がしたあと直前の話者を引き継いで補完してから比較する。ここを外すと話者一致率が壊滅するので、テストで固定する。

5-2. 指標（予稿 4.5）

指標定義
in 点|app.start - gt.start| <= --tolerance なら正解。既定 0.5 秒。閾値は複数まとめて渡せるようにし（--tolerance 0.3 0.5 1.0）、「許容できるずれは事前の試行で決定する」に使えるようにする。平均・中央値・最大の絶対誤差も出す。
話者一致対応付いた発話単位で app.speaker == gt.speaker か。正解率と件数。
false negative正解が登録話者なのに、アプリが Unknown_NN（または空欄）を付けた件数。
false positiveアプリが登録話者名を付けたが、正解と違う人だった件数（正解が未登録話者だった場合も含む）。
正しく Unknown正解も未登録話者で、アプリも Unknown_NN だった件数（誤りではないので別立てにする）。
混同行列--out-confusion で「正解話者 × アプリ話者」のクロス表を CSV に。どのキャラがどのキャラと取り違えられたかを見るため。

Unknown_NN の判定は正規表現 ^Unknown(_\d+)?$（大文字小文字を無視）と空欄。

6. アプリ本体の改修（RTTM 書き出し）

src/diarization/processor.py の process_and_save_to_csv に、話者分離結果の書き出しを1つ足す。

  • 出力先は output_csv_path の拡張子を .rttm に替えたパス（例 temp/transcription.csv → temp/transcription.rttm）。
  • 中身は標準的な RTTM 1行1区間。話者名はクラスタID（SPEAKER_00）ではなく照合後の話者名を入れる（self.assignments を通す）。これで RTTM 単体でも読める。
  • 書き出しに失敗しても本体の処理は止めない（実験用の副産物であり、字幕生成の成否とは無関係。既存の logger.warning にとどめる）。
  • Web UI と CLI は両方この関数を通るので、変更は1箇所。Spark も Web UI 経由で動かしているため追加のプラミングは不要。

7. やらないこと

  • 音声・動画の実際の切り出し（ffmpeg コマンドを出すところまで。誤爆すると重いので実行はしない）。
  • Unknown_NN の要因分類の自動化（聴取が必要）。
  • Web UI への組み込み（実験用の CLI に留める）。
  • 評価ツール側での pyannote 再実行（1-1 節の理由により、実行時に RTTM を残す方式にする）。
  • 正解字幕からの時間ベース重なり率の算出（重複区間が無いため不可能）。

9. 実装後に判明した事実と対応

9-1. アプリ生成字幕の話者表記は2形式ある（silent failure の回避）

実装中に temp/subtitles.srt を確認して判明した。アプリの出力には2つの話者表記がある。
  • (話者名)本文 … 最終字幕。src/subtitle/exporter.py の format_subtitle_text（半角括弧）
  • [話者名] 本文 … 仮字幕。src/web/converters.py の transcription_csv_to_srt
正解字幕では […] を効果音として無視する仕様なので、そのままでは後者を評価したときに全発話が false negative になり、しかもエラーにならない（0% が正しい測定値のように見える）。 そこで LabelRules.should_read_square_brackets を追加し、アプリ側の字幕だけ […] も話者ラベルとして読むようにした（アプリ出力の […] に効果音は入らない）。 tests/test_evaluator.py の TestCLIとアプリ字幕の話者表記 で両形式を固定している。

9-2. 実データ9本での確認結果（T8）

納品字幕9本すべてで動作を確認した。選定されたクリップの例:
